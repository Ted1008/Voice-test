# Voice-test — 語音輸入後處理修正 Sandbox

## 專案背景與目標

這是一個語音輸入（STT）後處理系統的 **概念驗證 Sandbox**。

語音辨識模型（如 Whisper）的輸出常出現同音異字錯誤，例如「滷肉飯」被辨識成「魯肉飯」。傳統字串替換無法處理這類問題，因為使用者的修正指令本身也是透過語音辨識輸入的，同樣可能有誤。

### 核心設計理念

```
使用者說話
    │
    ▼
[STT 模型 / Whisper]
    │ 輸出初步辨識文字（可能有同音錯字）
    ▼
暫存區（Indexed Buffer）
    │
使用者說修正指令（也經過 STT，也可能有誤）
    │
    ▼
[LLM]  ←── 暫存區 + 修正描述 + 拼音輔助資訊 + Tool 定義
    │ 輸出 function call
    ▼
執行 Tool → 更新暫存區
```

**關鍵設計**：暫存區以字元 index 標記每個字（`[0:我][1:想][2:吃]`），讓 LLM 精確定位操作目標，繞開 LLM 不擅長「數字元」的天生弱點。  
**拼音輔助**：同時提供修正描述與暫存區的拼音（`pinyin-pro`），讓模型在遇到同音字時能用聲調數字做可靠的音近比對。

## 快速開始

### 前置需求

- 靜態網頁伺服器（`npx serve` 或 VSCode Live Server）
- OpenAI API Key（需支援 function calling 的模型）

### 安裝與啟動

```bash
git clone https://github.com/Ted1008/Voice-test.git
cd Voice-test
npm install        # 安裝 pinyin-pro
npx serve .
```

瀏覽器開啟對應的本機地址（通常是 `http://localhost:3000`）。

## 介面說明（四個 Tab）

### 修正測試

基本的單筆測試介面：

1. 貼上 OpenAI API Key，選擇模型
2. 輸入（或選範例）初始句子，按「載入」
3. 輸入修正描述（模擬 STT 輸出），按「送出修正」
4. 觀察 log 區的拼音輔助資訊、function call 與執行結果
5. 頂部顯示目前使用中的 Prompt 版本名稱

### Prompt 編輯

**版本管理**（最多 5 個命名版本）：

- **另存新版本**：為目前 textarea 內容取名儲存
- **更新目前版本**：將 textarea 的修改覆寫回已選版本
- **載入版本**：從下拉選單切換版本（同步更新修正測試 Tab 的「使用中 Prompt」顯示）
- **重設為 prompt.txt**：回到預設內容

直接在 textarea 編輯時，若無選定版本，變更會自動草稿儲存至 localStorage。

### 測試記錄

每次「送出修正」自動記錄：

| 欄位 | 內容 |
|------|------|
| 時間 | 測試時間戳 |
| 模型 | 使用的模型名稱 |
| Prompt 版本 | 使用中的版本名稱（或「暫存」） |
| 修正指令 | 輸入的修正描述 |
| 暫存區（修正前） | buffer 原始內容與 indexed 結構 |
| Tool Calls 回傳 | LLM 回傳的 function call 詳情 |
| 修正結果 | 最終文字 |
| Prompt 完整內容 | 當時使用的 prompt 全文 |

點擊條目可展開查看完整詳情；支援匯出 **JSON**（完整資料）或 **CSV**（適合 Excel 跨版本比較）。

## 批次測試與 Prompt 自動優化

### 標準題組管理

維護一組可重複使用的測試題目，每題包含：暫存區、修正指令、預期結果（選填，用於 ✓/✗ 判斷）。

點「**載入預設 8 題**」可快速載入涵蓋各類修正情境的基準題組：

| # | 測試類型 | 暫存區 → 指令 → 預期 |
|---|---------|---------------------|
| 1 | 同音字替換 | 魯肉飯 → 水字旁的魯 → 滷肉飯 |
| 2 | 詞組替換 | 開欣 → 開心 |
| 3 | 詞組替換 | 利想 → 理想 |
| 4 | 同音詞替換 | 靠愛 → 可愛 |
| 5 | 成語定位 | 王 → 亡羊補牢的亡 |
| 6 | 刪除詞組 | 刪除真的 |
| 7 | 交換位置 | 爸媽 → 媽爸 |
| 8 | 拆字描述 | 木子李 → 李 |

### 批次執行

選擇 Prompt 版本與測試模型（可多選），按「開始批次測試」，系統依序跑完所有 **題目 × 模型** 組合，並以進度條即時顯示。支援取消（AbortController）。

結果顯示成 table（行 = 題目，列 = 模型），有預期答案的格子顯示 ✓/✗ 並計算各模型通過率；可匯出 CSV（每個模型各含結果欄 + 通過欄）。

### AI 驅動的 Prompt 優化迴圈

批次測試完成後，可勾選「**測試完成後自動 AI 分析**」（預設開啟）自動觸發分析。分析模型（預設 `gpt-4.1`，可換）會收到當前 prompt 全文 + 所有測試結果，輸出：

1. **失敗模式分析**：哪些題失敗、共同原因
2. **建議修改說明**：改了哪些部分及理由
3. **優化後的完整 Prompt**：可直接編輯後採用

**迴圈流程**：

```
開始批次測試
    │
    ▼ （自動）
AI 分析 ──→ 失敗模式 + 建議說明 + 新 Prompt（可編輯）
    │
    ▼ （人工審查，唯一需要參與的步驟）
[接受並進入下一輪] ──→ 自動儲存為 AI優化-rN → 自動跑下一輪批次測試
[放棄此建議]       ──→ 停止迴圈
```

每輪通過率以「優化歷程」chips 呈現，方便追蹤改版效果：

```
優化歷程：  [原版 50%]  [AI優化-r1 75%]  [AI優化-r2 87%（目前）]
```

## 架構細節

### 暫存區（Indexed Buffer）

```
「我想吃魯肉飯」→ [0:我][1:想][2:吃][3:魯][4:肉][5:飯]
```

每次 tool 執行後，會重新打散成單字元 token，確保 index 永遠對應單一字元。

### Tool 定義

| Tool | 參數 | 說明 |
|------|------|------|
| `replace` | `start_index`, `end_index`, `new_text` | 替換一段連續字元；`new_text` 為空字串等同刪除 |
| `insert` | `index`, `text` | 在指定位置前插入文字 |
| `swap` | `index_a`, `index_b` | 交換兩個字元的位置 |

> `delete` 已廢棄，統一用 `replace` + 空字串，避免模型混用造成 index 偏移。

### 多 Tool Call 執行順序

LLM 回傳多個 function call 時，前端依 index **由後往前排序**執行，避免先執行前面的操作導致後面的 index 位移。

## 模型測試結論

針對「成語描述同音字」這個最難 case（例如「王改成亡羊補牢的亡」）的各模型表現：

| 模型 | 一般同音字修正 | 成語描述定位 | 備註 |
|------|-------------|------------|------|
| gpt-5-nano | ❌ | ❌ | 直接把描述塞進暫存區 |
| gpt-5-mini | ⚠️ | ❌ | 理解任務但推理不足 |
| gpt-4o-mini | ⚠️ | ❌ | 容易產生多餘操作 |
| gpt-4.1-mini | ✅ | ❌ | 日常修正穩定，成語推理失敗 |
| gpt-4.1 | ✅ | ✅ | 目前通過所有測試的最低門檻 |

**建議**：日常修正用 `gpt-4.1-mini` 即可；需處理成語定位等複雜推理時使用 `gpt-4.1`。批次測試時建議兩者都選，直接比較結果。

## Prompt 調教

`prompt.txt` 是本專案最核心的調教對象，目前包含：

- **思考步驟**：要求 LLM 先推斷目標句、發音比對、最小 diff，再呼叫 tool
- **容錯匹配規則**：修正描述與暫存區都可能有 STT 誤辨，優先根據拼音定位
- **成語/詞組定位規則**：從成語中找音近字，並處理「亡羊補牢的王」這類語音辨識造成的邏輯矛盾
- **拆字/部首描述**：處理「木子李」「三點水加古」等描述方式
- **8 個 few-shot 範例**：涵蓋同音字、範圍替換、刪除、成語定位、插入、交換等情境

透過 **Prompt 版本管理**，可同時維護最多 5 個命名版本，搭配批次測試快速比較各版本的通過率。

## 已知限制與未來方向

### 已知限制

- **STT 尚未接入**：目前用手動文字模擬 STT 輸出，真實場景的錯誤分佈可能不同
- **成語描述 mini 模型不穩定**：需要較強推理能力的模型
- **正文不支援 LLM 修正**：Commit 進正文後只能手動 UI 操作

### 下一步方向

- 接入 Whisper API 或本地 faster-whisper 做真實 STT 測試
- 評估 Anthropic Claude 作為修正模型的可行性
- 雙按鈕 UI 設計（輸入模式 / 指令模式分離）
- 手機端部署評估
